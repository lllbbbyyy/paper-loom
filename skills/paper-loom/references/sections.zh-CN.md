# 围绕读者问题组织章节

## 摘要：压缩论证链，而不只是压缩字数

可采用“**背景与需求 → 已有选择及剩余困难 → 方法与区别性机制 → 有证据的结果及意义**”的链条。短摘要可以让一句承担相邻功能，但应保留足够背景，让小领域之外的读者理解为什么需要这个方法。

篇幅紧张时，先删除工具名、参数、过程计数和次要指标，再考虑删减问题为何困难的解释。每个数值对应明确的参照和指标。结果尚未获得时，保留工作占位或省去实证主张，不能把计划比较写成发现。先确定各句逻辑功能，再分配字数。

## 引言：建立科研故事

引言回答一组逐步推进的读者问题。下表是功能选项，不是必须写八段的模板。

| 功能 | 读者的问题 | 常见的后续连接 |
|---|---|---|
| 大背景 | 涉及什么重要活动或目标？ | 该活动需要某种能力。 |
| 具体需求 | 现有方式提供这种能力为何昂贵或困难？ | 不同方法尝试满足这一需求。 |
| 研究现状 | 当前方案按什么思路或假设组织？ | 各自权衡留下了与任务有关的问题。 |
| 缺口 | 在什么条件下，还有什么没有解决？ | 解决它需要克服可辨认的挑战。 |
| 挑战 | 为什么这件事困难，而不只是尚未实现？ | 某项观察提示了应对方式。 |
| 洞察 | 什么关系改变了问题的处理方式？ | 该关系引出具体设计选择。 |
| 方案 | 这些设计如何配合？ | 可以明确贡献及验证它们的证据。 |
| 贡献 | 建立了什么新能力或认识？ | 正文解释机制并检验主张。 |

每段用主题句突出主要观点，后续句子建立、限定或展开它。段末留下的概念或问题应当由下一段真正接起。不要刻意制造悬念，不默认用虚构情境开头，也不要让读者迟迟找不到研究问题。

### 相关工作的分类

选择能够解释当前问题的共同维度，例如使用的信息、建模假设、优化目标或分解层次。不要把模型类别、应用领域和发表年份混作同层分类。先用大同行能理解的名称说明类别，再列代表工作。

对相关类别说明：它擅长处理什么，什么条件下还有困难，这项困难为什么与本文有关。每种概括需要文献依据。可以在若干类别之后统一归纳不足，不必在每条引用后机械加入“但这些方法都失败了”；这种说法通常也不准确。

好的分类覆盖与当前任务有关的主要选择，必要时解释重叠和范围，不要求互斥或穷尽整个领域。有实质关系时把类别与挑战对应起来，允许多对多。不能因为有三类工作就编出三个挑战。

### 挑战与洞察

挑战是目标能力难以获得的原因。“需要一个数据模块”只是任务清单；“标注昂贵，而均匀采样容易漏掉罕见失效区间”才说明了需要特定数据策略的困难。

洞察是有依据的观察或论证关系，它会改变设计决策。“提出一个框架”给出了贡献名称，但没有说明洞察。区分待验证假设与动机实验已经支持的观察。先解释洞察为什么引出机制，再命名模块。

## 方法：先说明目的，再展开机制

开头交代任务输入、输出、假设及各部分的配合方式。每个主要机制说明：

1. 回应哪个挑战。
2. 做出什么设计选择。
3. 为什么这种选择能够应对挑战。
4. 接收和产生什么信息。
5. 哪些细节是理解、实现或评价所必需的。

读者理解模块作用后再使用模块名称。控制流或数据流难以理解时，可用图或简短算法说明。目标函数、决策规则、接口和适用条件应保留在正文。配置清单、提示词和重复参数在投稿形式允许时放入配套材料。可读性不能成为隐藏核心机制的理由。

## 实验：用证据回答问题

增加实验前先完成主张与实验的对应。常见问题包括整体有效性、提升来源、声明范围内的泛化和实际权衡，选择本文主张需要的部分，不机械要求四项齐全。

每个实验记录：被检验的主张、问题、基线或控制、共同条件、指标、结果状态，以及该比较能够支持的解释。消融对机制的支持取决于其他相关条件是否得到控制。案例可以解释行为，但不能自动证明普遍优势。

正文按“**问题 → 必需的比较设置 → 结果 → 含义**”展开。说明误差、开销或加速是越大越好还是越小越好，以及相对于谁。会改变结论的不确定性或不利结果需要报告。执行日志、文件数量和底层调参记录通常放到主叙事之外，除非它们本身就是主张的一部分。

## 讨论与结论

讨论解释已展示的机制何时有用、哪些权衡值得关注、什么假设会影响结果解释。必要范围条件在适当位置说清楚，不反复插入泛泛的免责声明。

结论回到研究问题，说明已经建立的能力或发现，以及它在评价范围内的意义。不能增加新机制、新结果或比正文更强的主张。最后一句可以直接结束论证，不必再引出新章节。
